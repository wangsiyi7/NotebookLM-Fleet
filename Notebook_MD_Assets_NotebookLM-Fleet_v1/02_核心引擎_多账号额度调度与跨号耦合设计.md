# 02 · 核心引擎：多账号额度调度与跨号耦合设计

## 一、精细化额度采集引擎（`quota_poller.py`）

不同于粗粒度的“成功/报错”试探，系统通过 `notebooklm-py` 直接读取账号的底层使用量接口，每个采样周期持久化以下维度：
- **双周期窗口**：`FIVE_HOUR`（5 小时滚动/重置窗口）与 `WEEKLY`（7 天周上限窗口）各自的 `used_percent`、`remaining_percent` 与 `resets_at`（ISO-8601 时间戳）。
- **细粒度动作配额矩阵（22 项动作）**：包含 `audio_overview`、`video_overview`、`breakdowns_video`（cinematic_video）、`slides`、`quiz`、`flashcards`、`infographic`、`mindmap`、`reports`、`tables`、`qna` 等。每项均记录：
  - `has_sufficient_quota`（当前窗口是否可执行）
  - `estimated_cost_percent`（预估单次消耗百分比）
  - `remaining_deferred_artifact_generations`（是否还有官方“稍后生成 / Generate Later”槽位）
- **实测扣费闭环**：每次 Studio 或 Chat 任务执行前后，调度器记录 `pre_five_used` 并立刻再触发 `poll_one_account`，将真实增量写入 `tasks.actual_delta_5h_pct`，形成“预估 vs 实测”校准基准。
- **每日无锁在线热备**：每轮全部轮询结束后，`_maybe_run_daily_backup()` 检查距上次备份是否已满 24 小时，并通过 `asyncio.to_thread` 异步调用 `sqlite3.Connection.backup()` 备份至 `NLM_Hub\00_System\backups\`。

## 二、分档、窗口与防风控调度算法（`scheduler.py`）

后台每 10 秒运行一次 `run_scheduler_tick()`，核心路由决策函数为 `select_account_for_task()`。

### 1. 候选账号准入过滤
对于每条 `pending` 或已到 `scheduled_after` 的 `waiting_quota` 任务，必须依次通过以下刚性校验：
1. `enabled == 1`（未被台账暂停）
2. **双通道准入校验**：拥有有效 `nlm_auth_status == 'ok'`，或者当任务属于官方 API 支持范围（`ingest_url` / `ingest_text` / `ingest_file`）且全局启用了官方 API 时拥有 `official_oauth_status == 'ok'`。
3. **单号严格串行锁**：账号不在当前数据库 `busy_account_ids`（无正在运行的 `running` 任务）。同号连续下发之间额外执行 `random.uniform(task_delay_min_sec, task_delay_max_sec)`（默认 **8–18 秒随机间隔**），同时在 `nlm_py_adapter` 层持有按 `(event_loop_id, profile_name)` 划分的 `asyncio.Lock`。
4. **档位硬门槛与源数量容量校验**：校验 `tier_requirement`（`any` / `ultra` / `pro_plus`）与 `source_count <= source_limit`（默认 Ultra 600 源 / Pro 300 / Plus 100 / Free 50，防止超出低档位上限）。

### 2. 综合评分模型与 3 种全局策略
在所有通过过滤且满足 `(five_rem - est_cost) >= safety_buffer_pct`（默认留 10% 余量）及 `weekly_rem >= 5.0%` 的账号上计算得分：

$$\text{Score} = W_{\text{tier}}(\text{policy}, \text{task}) + \text{WindowUrgency} + 0.2 \times \text{weekly\_rem} + 0.05 \times \text{five\_rem} + \mathbb{I}_{\text{preferred}} \times 500$$

- **全局策略（`tier_policy`）**：
  - `conserve_ultra`（默认推荐）：重任务（`cinematic_video` / `video` / `audio` / `slide_deck`）赋予 Ultra 最高权重（100 vs 50/30/10）；轻任务（`quiz` / `flashcards` / `chat` 等）反而把 Free/Pro 置于 Ultra 之前（70/50 vs 10），保护高价值 Ultra 算力。
  - `ultra_first`：无论轻重任务全部优先打满 Ultra。
  - `balanced`：屏蔽档位偏置，纯粹按即将重置紧迫度和剩余额度均衡分摊。
- **快重置优先（`WindowUrgency`）**：若当前 5 小时窗口即将在 $H \in [0, 5]$ 小时内重置，加分 $(5.0 - H) \times 6.0$，优先用掉“快作废”的临期 5 小时额度。

### 3. 四态决策分支
1. `run`：选中最高分空闲账号立即执行。
2. `deferred_later`：无即时额度，但若任务属于 `LATER_SUPPORTED_TASKS` 且某账号持有 `remaining_deferred_artifact_generations > 0`，自动开启 `--later` 提交至官方延时队列。
3. `waiting_quota`：无即时与延时槽位，计算所有候选账号中**最早**的 `five_hour_resets_at + 2 分钟`（若未知则 +15 分钟）写入 `scheduled_after`，到点自动重入队执行。
4. `no_eligible_account`：暂无任何可用登录/开启账号，保持 `pending` 等待用户上线账号。

## 三、跨账号耦合引擎（`coupling.py`）

为了避免同一学习主题在 6 个 Ultra 账号之间“资料不一致”或“产物各自散落”，系统在 `ensure_topic_notebook_for_account()` 实现了两级耦合协议：

1. **一级模式 · 主本共享 Editor（`shared`）**：
   - 若主题在主账号上已创建主笔记本（`notebooks.is_master = 1`），当队列调度另一个闲置工作账号来分担生成时，系统先调用主账号把工作账号邮箱添为 **Editor**（不发打扰邮件 `notify=False`）并记录 `shared_emails_json`，随后工作账号直接针对同一 `remote_notebook_id` 发起生成，耗费各自窗口额度，但共享同一份 Source 上下文。
2. **二级兜底 · Google Drive Hub 独立镜像（`drive_mirror` / `shared_with_drive_fallback`）**：
   - 在推荐模式 `shared_with_drive_fallback` 下，如果某项 Studio 动作因共享协作者权限限制失败，`scheduler.py` 会自动捕获异常、切换 `force_mirror=True` 在该工作账号下新建镜像笔记本（`"<主题名> (<alias>)"`），自动读取本地云盘 `02_Topics/<主题>/Sources/` 中的原始文件全量导入后重新执行生成，最终将产出的 `.m4a`/`.mp4`/`.pdf`/`.md` 统一写回主盘唯一的 `Artifacts/` 文件夹。

## 四、异常恢复与重启自愈

服务异常重启或强杀时，`app/main.py` 在 `lifespan()` 启动初始化阶段会第一时间把所有残留处于 `status = 'running'` 的孤儿任务重置为 `status = 'pending'`、`assigned_account_id = NULL`、`started_at = NULL`，确保恢复后不会因虚假占锁导致整个账号被调度器长期跳过。
